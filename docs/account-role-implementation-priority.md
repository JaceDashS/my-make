# 계정/권한 기능 구현 우선순위

## 목적

이 문서는 아래 17개 요구사항을 기준으로, **현재 `my-make` 프로젝트에서 무엇을 먼저 구현해야 하는지**를 정리한다.

우선순위 기준은 다음 네 가지다.

1. 현재 저장소에 이미 일부 구현이 존재하는가
2. 다른 기능의 선행 조건인가
3. 운영 리스크를 줄이는 핵심 흐름인가
4. UI와 API를 짧은 배치로 끝낼 수 있는가

## 권장 구현 순서

### 0단계. 기반 정리

대상 요구사항:

- [x] 기능 1 목적별 아카운트
- [x] 기능 2 root 권한
- [x] 기능 4 admin 권한
- [ ] 기능 5 teacher 권한
- [ ] 기능 6 student 옵션

이번 단계 목표:

- 역할별 기능 매트릭스 확정
- API 단위 권한 체크 위치 통일
- 화면 메뉴 노출 규칙 통일

이 단계를 먼저 두는 이유:

- 현재는 역할 데이터와 일부 상태 전환은 있지만, 기능 접근 제어가 화면과 서버에서 완결되지 않았다.
- 이후 예약, 재고, 수강권, 감사로그를 만들더라도 역할 경계가 먼저 고정돼야 재작업이 줄어든다.

산출물:

- 역할별 capability 표
- 서버 공통 권한 검사 규칙
- 클라이언트 메뉴/화면 가드 규칙

우선순위:

- `P0`

### 1단계. 가입-승인-프로필 흐름 완성

대상 요구사항:

- [x] 기능 7 라이선스 등록
- [x] 기능 8 root 계정 등록
- [x] 기능 9 admin / teacher / student 등록 및 승인
- [x] 기능 10 프로필 조회 및 수정
- [x] 기능 11 사용자 상태

현재 상태:

- 대부분의 백엔드와 일부 프런트 흐름이 이미 있다.
- 다만 운영 시나리오 기준으로 보면 "완성"이 아니라 "기초 골격" 수준이다.

이번 단계에서 마무리할 것:

- root 등록 화면과 검증 흐름 마감
- admin / teacher / student 가입 화면 정리
- 승인 대기 목록과 승인 액션 UX 마감
- academy 멤버 검색과 상태 변경 화면 마감
- 라이선스 등록과 갱신 운영 플로우 정리
- 프로필 수정 권한을 역할별로 명시적으로 제한

이 단계가 먼저여야 하는 이유:

- 이 흐름이 안정되지 않으면 teacher, student, admin 데이터를 계속 만들 수 없다.
- 이후 모든 기능은 "소속 academy에 속한 승인된 계정"을 전제로 한다.

산출물:

- 운영 가능한 계정 lifecycle
- academy 소속 승인 프로세스
- 로그인 가능 상태와 불가 상태의 명확한 규칙

우선순위:

- `P0`

### 2단계. 커스텀 권한 위임

대상 요구사항:

- [ ] 기능 3 커스텀 권한 위임

현재 상태:

- `AUTH_POLICY` 저장 컬럼은 존재한다.
- 하지만 실제 권한 문서 구조, 파서, 평가 로직, 화면 편집기는 없다.

이번 단계에서 구현할 것:

- 권한 문서 JSON 스키마 정의
- root가 admin에게 세부 권한을 위임하는 편집 UI
- 서버 단 접근 제어에서 역할 기본 권한 + 위임 권한 합성
- 감사 가능한 정책 변경 이력 준비

이 시점에 구현하는 이유:

- 너무 초기에 넣으면 계정 기본 흐름 구현이 느려진다.
- 너무 늦게 넣으면 예약, 수강권, 재고 관리에 다시 권한 레이어를 덧씌워야 한다.

우선순위:

- `P1`

### 3단계. teacher 준비 데이터

대상 요구사항:

- [ ] 기능 12 수업용 preset 관리
- [ ] 기능 13 타임슬롯 관리 중 teacher 설정 영역
- [x] 기능 14 학생 피부 데이터 입력

현재 상태:

- 학생 피부 데이터는 저장 구조와 UI 초안이 있다.
- teacher의 preset / available schedule은 DB 컬럼만 있고 실질 기능은 없다.

이번 단계에서 구현할 것:

- teacher preset CRUD
- preset과 학생 피부 데이터의 기본 적합성 계산
- teacher 주간 가능 시간 설정
- 휴가 / 부재 예외 시간 설정
- root / admin의 teacher preset, schedule 조회/관리 범위 정의

이 단계가 예약보다 먼저여야 하는 이유:

- 예약은 teacher가 공개한 시간과 preset 정보가 있어야 의미가 생긴다.
- 학생 피부 데이터와 teacher preset 연결 규칙이 먼저 있어야 예약 UX가 단순해진다.

- `P1`

## 구현 시 주의점

- `root`와 `admin`의 차이는 단순 역할명이 아니라, "기본 권한"과 "위임 가능 권한"으로 분리해서 설계해야 한다.
- `teacher`의 타임슬롯은 예약 엔티티와 분리된 원본 가용성 데이터로 유지하는 편이 안전하다.
- `student` 피부 데이터와 `preset` 적합성 판단은 "권고"여야 하며, 요구사항대로 불일치 상태에서도 진행 가능해야 한다.
- 사용자 상태 `hold`는 로그인은 가능하지만 일부 액션 제한이라는 점을 API 단위로 명확히 정의해야 한다.
- 감사 로그는 마지막 배치로 두더라도, 지금부터 각 도메인 서비스 호출 지점에 이벤트 훅을 넣기 쉬운 구조로 정리해 두는 것이 좋다.
