# MAIMEI 色相マッチング / PRESET 上位構造 Handoff

## 1. 文書の目的

本書は `maimei` の色相マッチングおよび PRESET 関連の上位設計構造を整理するための handoff である。

本書の目的は次のとおりである。

* 何をどの責務単位に分けるかを整理する
* 色相判定モデルと運用原則を整理する
* MVP と拡張方向を整理する
* 今後 Oracle schema を設計するための基準線を提供する

本書は **DB schema 確定文書ではない。**
つまり、本書は **「何を作るか」を整理する文書** であり、
**「DB にどう保存するか」まで完全に確定する文書ではない。**

## 2. この文書で確定したこと

### 2.1 責務分離

色相マッチング関連の責務は次の単位に分離する。

* `Student`
* `SKU`
* `PRESET`
* `Category`
* `Shade Zone`

各単位は 서로 다른 역할을 가진다.

### 2.2 色相判定モデル

色相判定は **LCH 基準** で行う。

* HEX は最終表示や入力補助には使えても、核心判定モデルにはしない
* 学生の肌色、SKU 色相、許容領域の判定は LCH 基準で考える

### 2.3 運用原則

色相適合性は **自動推薦方式では判定しない。**

システムが自動で推薦式を計算する方式ではなく、

* 運用者が許容範囲を直接定義し
* システムは SKU がその範囲内に入るかだけを判定する

構造で進める。

つまり、この構造は **運用者定義領域ベースの包含判定構造** である。

### 2.4 拡張方向

許容領域 (`Shade Zone`) の表現は次の段階で考える。

* **MVP**: `circle`
* **拡張**: `polygon`

初期は単純な円形範囲から始め、必要になれば多角形領域へ拡張する。

## 3. 責務単位別の構造

### 3.1 Student

#### 役割

学生は色相判定の **基準点** である。

#### 構造原則

* 学生は **単一代表肌色** のみを持つ
* 学生は複数の肌色セットや複数パレットを持たない
* 学生は複雑な推薦ロジックの主体ではなく、比較の基準になる主体である

#### 意味

> Student は「何が似合うかを判定するための基準肌色 1 個」を持つ

### 3.2 SKU

#### 役割

SKU は実際の化粧品識別単位であり、色相比較の対象である。

#### 構造原則

* すべての化粧品は SKU 単位で管理する
* 塾に配置された化粧品はすべて SKU を持つ前提とする
* 色相判定が必要な場合、SKU は LCH 情報を持つ

#### 意味

> SKU は製品情報と色相情報の源泉単位である

### 3.3 PRESET

#### 役割

PRESET は講師が運用上使用する **製品組み合わせ** と **許容規則** を表現する。

#### 構造原則

PRESET は概念的に次の二つを持つ。

1. **SKU の束**
   * 実際に使用する品目の組み合わせ
2. **許容規則**
   * どの色相範囲を適合とみなすかの運用ルール

#### 意味

> PRESET は製品そのものではなく、「どの SKU の束をどの条件で使うか」を表現する運用単位である

### 3.4 Category

#### 役割

Category は巨大な化粧品分類体系ではなく、
**色相適合性判定が必要な最小区分単位** である。

#### 構造原則

* 全化粧品を最初から強く標準化しない
* 基本的には **必須のものだけをデフォルト category として持つ**
* 残りは運用者が必要に応じて追加できる方向で考える

#### 基本対象例

* foundation
* cushion
* concealer
* corrector

#### 意味

> Category は完全 taxonomy ではなく、適合性判定のための最小運用単位である

### 3.5 Shade Zone

#### 役割

Shade Zone は運用者が定義する **許容色相領域** である。

#### 構造原則

* 自動推薦ではなく運用者手動定義方式
* SKU がこの領域に入れば適合とみなす
* LCH 全体を直接 3D で扱うより、構造上は `領域 + hue 範囲` の概念で 접근する

#### MVP / 拡張

* MVP: circle
* 拡張: polygon

#### 意味

> Shade Zone はシステムが計算した結果ではなく、運用者が直接定めた許容範囲である

## 4. 全体関係構造

全体構造の意味は次のとおりである。

* **Student** は基準肌色を持つ
* **SKU** は実際の製品と色相情報を持つ
* **PRESET** は SKU 束と許容規則を持つ
* **Category** は色相判定が必要な最小単位を区分する
* **Shade Zone** はどの色相を許容するかを定める

つまり、全体構造は次の流れで理解する。

```text
Student = 基準点
SKU = 比較対象
PRESET = SKU 束 + 許容規則
Category = 判定対象区分
Shade Zone = 運用者定義許容領域
```

## 6. この文書の位置づけ

この文書は次の性格を持つ。

* **アーキテクチャ handoff としては十分有効**
* **DB schema handoff としてはまだ不十分**

つまり、この文書は実際の schema 設計前段階の基準文書として使用する。

## 7. schema 確定前に追加で必要な文書

実際の Oracle schema に落とすには最低限、次の文書が追加で必要である。

1. `PRESET JSON 契約書` または `PRESET テーブル構造`
2. `SKU 最小カラム定義`
3. `Shade Zone 保存フォーマット定義`

## 8. 最終要約

一行で要約すると次のとおりである。

> この handoff は **何を作るか** は定めるが、**DB にどう保存するか** まではまだ定めない

つまり、現段階で確定したものは次である。

* 責務分離
* LCH 基準
* 運用者定義領域ベース判定
* MVP は circle、以後 polygon 拡張

そして、まだ残っているものは次である。

* 実際のテーブル構造
* カラム構造
* FK 関係
* 保存フォーマット
